# Edit production springs in four reversible layers

You can slow, pause, scrub, edit and cleanly revert flora.so's carousel spring on the live production page, and most of it needs neither a reload nor the debugger infobar. Build it as four layers, in this order. **First, a library-agnostic floor**: record the element that actually moves, fit a spring to it, and preview the edit as a WAAPI `linear()` animation that sits on top of the page's own motion and cancels without a trace. Flora's recordings fit back to **0.542–0.555 s and bounce 0.155–0.163**, against the true 0.55 / 0.16. **Second, a MAIN-world virtual clock** injected on demand, which slowed flora's real spring to **0.25× with the overshoot unchanged at 2.22 px** and hands time back through a `release()` that lets the current move finish first. **Third, library adapters, Motion first**: read the authored transition from React fibers, override `getDefaultTransition` on the live VisualElement, replay the move through Motion's own pipeline, and on motion-dom 13.3.0 or later use Motion's undocumented `__MOTION_INSPECT__` hook to pause, seek and re-speed individual animations. **Fourth, CDP**, kept for an opt-in "reload to include timers" mode and for expert fallbacks such as heap discovery and side-effecting breakpoints. Two CDP features are off the table: `Debugger.setScriptSource` no longer exists (removed in Chrome 145), and `Emulation.setVirtualTimePolicy` broke the tab's clock in a way that survived both detach and reload. Give the coding agent the transition in the source's own form, because flora writes `duration` and DialKit's spring control has no `duration` field, together with the fit, its error and grep keys, because flora serves no source maps. Every measurement here comes from scripts executed in headless Chromium 158 against live flora.so on 2026-11-25; nothing has run inside Snapshot itself, in headful Chrome, Edge or Dia, so a short validation pass in the real extension comes before the build. Proof scripts are cited as `scripts/…`, relative to `extension/research_notes/Previewing JavaScript animation edits/`, so you can rerun them.

## Flora runs motion-dom 14.1.0 on a five-second autoplay

### The carousel is a JS-driven `motion.div` fed by a production DialKit hook

Flora is a Next.js 16.4.0 site with Turbopack chunks, rendered by a React 19.3.0 canary (the `reconcilerVersion` string in its chunk). Its carousel is a plain `motion.div` with `animate: {x: -m*j + y}` and `transition: {type: "spring", duration: f.motion.springDuration, bounce: f.motion.springBounce}`, which collapses to `{duration: 0}` while you drag or under reduced motion ([flora chunk](https://flora.so/_next/static/immutable/chunks/43t38g6et1zz8.js)). The values come from a DialKit hook bundled into production, `useDialKit("Journal carousel", …)`, whose dials default to `springDuration .55`, `springBounce .16` and an autoplay `interval` of 5 s on a 1.5–12 s range. That detail pays off at hand-off time, because the authored numbers and their label survive minification as string keys.

The spring runs on the JS thread: `getAnimations()` returns nothing in any moving frame, and Motion rewrites the inline `transform` every frame (`scripts/fit-flora-sample.mjs`, `scripts/clock-cdp-knobs.mjs`). The baseline step **moves 288 px every 5 s in 563–567 ms, overshoots 2.20–2.22 px and settles within 0.5 px at 536–544 ms** (`scripts/debugger-live-patch-flora.mjs`, `scripts/library-flora-motion-fiber.mjs`). The element that moves is the track, `div.absolute` inside `.journal-carousel .t-panel-slide`. The slide `<article>` a person clicks has no transform of its own, and React rewrites its `left` one frame before each move, so **the selected element and the element that owns the motion are different** (`scripts/fit-flora-sample.mjs`).

### Three notes disagree on the version, and only 14.1.0 has evidence on both sides

Flora ships no version string, so each researcher compared its chunk against npm tarballs, and they reached three answers.

| Claim | Evidence used | Weakness |
|---|---|---|
| ≥ 13.3.0 and < 14.14.0 | inspector hook present; `value.run(` absent from `animateTarget` (it first appears in 14.14.0) | wide range |
| ≥ 14.0 | `isTimeDefined`, `delayState` and `manualStartTime` present; 13.3.0 lacks `isTimeDefined` | no 13.4 or 13.5 tarball checked, and 13.5.1's spring already has `isTimeDefined` ([13.5.1 spring.mjs](https://unpkg.com/motion-dom@13.5.1/dist/es/animation/generators/spring.mjs)) |
| exactly 14.1.0 | `resolveStartTime` present (first in 14.1.0); `TransformAnimation` absent (first in 14.2.0); the velocity rescale added in 14.1.1 absent | still a feature diff, not a version string |

**14.1.0, released 2026-10-09, is the best-supported answer.** It is the only claim bracketed from below and above, by a feature that first appears in 14.1.0 and two that first appear later, and it sits inside both other ranges ([motion-dom 14.1.0 batcher](https://unpkg.com/motion-dom@14.1.0/dist/es/frameloop/batcher.mjs), [14.2.0 TransformAnimation](https://unpkg.com/motion-dom@14.2.0/dist/es/animation/waapi/transforms/TransformAnimation.mjs), [14.1.1 create-generator-easing](https://unpkg.com/motion-dom@14.1.1/dist/es/animation/generators/utils/create-generator-easing.mjs), [npm registry](https://registry.npmjs.org/motion-dom)). The exact patch number changes nothing in the design, but the two bounds do. From 13.3.0 the inspector hook exists. Before 14.2.0, Motion cannot hand an `x` transform to WAAPI, which is why flora's spring runs on the JS thread. On a site running 14.2 or later, the same carousel can run as a WAAPI `TransformAnimation`, and a different layer then controls it, as the Motion adapter section explains.

### Four runs measured a 5 s cadence, not the brief's 3 s hold

The brief's "holds ~3 s at −1152 px" does not reproduce. Flora's source starts autoplay with `window.setInterval(…, 1000 * interval)`, with `interval` defaulting to 5 and gated on the card being 45% in view ([flora chunk](https://flora.so/_next/static/immutable/chunks/43t38g6et1zz8.js)). Four independent harnesses measured exactly that: autoplay starts at 6763, 11762 and 16761 ms, 5.0 s apart (`scripts/library-flora-motion-fiber.mjs`); a 4.45 s hold between 550 ms moves (`scripts/fit-flora-preview.mjs`); and a 5 s cadence in both the clock and the debugger harnesses. **Treat 5 s as correct.** The positions in the brief are only where the carousel index happened to be, since it moves 288 px per step and loops, and the preview run itself replayed −1152 → −1440. The 3 s figure could come from a different `interval` dial value or a manual advance, but nothing verified either. In practice, "preview on next trigger" can wait up to five seconds on flora, so an on-demand replay is the better default.

### Every working technique reproduced the 46.9 px that bounce 0.5 predicts

Each technique below changed the spring on the production page without a reload and reverted to the baseline numbers. The edits match the physics: with Motion's damping ratio ζ = 1 − bounce, bounce 0.5 predicts an overshoot of 16.3% of 288 px, or 46.9 px, and every technique that set bounce 0.5 measured about that.

### Motion reads its clock and its hook at call time, which overturns two predictions

The prior art predicted that a late clock could not control Motion, and execution proved it wrong. Motion captures `requestAnimationFrame` once, when its module loads ([frame.mjs](https://unpkg.com/motion-dom@14.1.0/dist/es/frameloop/frame.mjs)), which made a clock injected after load look useless. But Motion's batcher ignores the rAF timestamp: unless `useManualTiming` is set, it calls the global `performance.now()` afresh on every frame, and `JSAnimation` computes the spring purely from that elapsed time ([batcher.mjs](https://unpkg.com/motion-dom@14.1.0/dist/es/frameloop/batcher.mjs), [JSAnimation.mjs](https://unpkg.com/motion-dom@14.1.0/dist/es/animation/JSAnimation.mjs)). Overriding `performance.now` after load therefore controls the spring completely. The same detail explains why the freeze features in two agent-annotation tools miss Motion. Agentation and react-grab wrap `window.requestAnimationFrame` when they mount or load, while Motion keeps calling the native rAF it saved earlier, so its callbacks never pass through their wrappers ([Agentation freeze-animations.ts](https://github.com/benjitaylor/agentation/blob/main/package/src/utils/freeze-animations.ts), [react-grab freeze-animation-frame-loops.ts](https://github.com/aidenybai/react-grab/blob/main/packages/react-grab/src/utils/freeze-animation-frame-loops.ts)).

The second overturned prediction is that the inspector hook needs document start. Motion's own Playwright test installs it with `addInitScript`, before page scripts run ([inspect-playback.spec.ts](https://github.com/motiondivision/motion/blob/main/tests/react/inspect-playback.spec.ts)), but `notifyAnimationStart` reads `globalThis.__MOTION_INSPECT__` on every call ([notify-inspector.ts](https://github.com/motiondivision/motion/blob/main/packages/motion-dom/src/animation/utils/notify-inspector.ts)). A hook defined after `networkidle` fired on the next autoplay (`scripts/library-flora-motion-inspector.mjs`). Installing at document start only adds the animations that start while the page loads, which was 11 records in flora's first 8 s.

### LiveEdit is gone, virtual time wrecks the tab, and the CSS knobs never touch rAF motion

`Debugger.setScriptSource` refused every variant with `setScriptSource functionality no longer available`: `dryRun`, `allowTopFrameEditing`, `--js-flags=--inspector-live-edit`, and `chrome.debugger.sendCommand` from a real MV3 extension (`scripts/debugger-live-patch-flora.mjs`, `scripts/debugger-extension-probe-flora.mjs`). That matches Chrome's deprecation in version 142 and removal in 145 ([Chrome blog](https://developer.chrome.com/blog/devtools-deprecates-live-editing)) and V8's removal of the inspector's live-edit support ([Node.js V8 notes](https://nodejs.org/en/blog/announcements/notable-v8-changes-from-node-js-26-to-27-alpha)). `Emulation.setVirtualTimePolicy` is built for headless capture and has no "real time × rate" mode ([CDP Emulation](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/#method-setVirtualTimePolicy)). Its `pause` policy stopped even `setTimeout(0)`, and its `advance` policy ran **13.7–18.3 million ms of page time in 8 s**, staying broken after detach, a fresh session and a reload (`scripts/clock-cdp-knobs.mjs`, `scripts/clock-cdp-inject.mjs`).

`Animation.setPlaybackRate(0.25)` slowed a CSS probe but left the carousel at 553–577 ms, and 6× CPU throttling left it at 571–608 ms (`scripts/clock-cdp-knobs.mjs`). Chrome's own Animations panel states the limit plainly: "requestAnimationFrame animations are not yet supported" ([Chrome DevTools](https://developer.chrome.com/docs/devtools/css/animations)). Two page-level shortcuts failed as well. Changing `ve.props.transition` was lost on the next render, because flora passes a new transition object every time (`scripts/library-flora-motion-fiber.mjs`), and an inline `!important` preview lost its priority on Motion's next per-frame write (`scripts/fit-flora-preview.mjs`).

## Build four layers in order: floor, clock, library adapters, then CDP

### Universal techniques first, library internals second, the debugger last

Two techniques work on every page, and everything else adds speed or fidelity on top. Every library ends up either writing a style that a WAAPI animation can override or reading a clock that a MAIN-world script can replace. Library handles are more faithful, but each relies on internals that a minor release can rename. CDP reaches anything, but it costs a visible infobar and your extension's single debugger connection to the tab, and some of its patches survive detach. So build up from the two universal techniques.

| Order | Build | What you get | Runs via | Hard limit |
|---|---|---|---|---|
| 0 | Plumbing: packaged MAIN-world installers, nonce event channel, one undo ledger per tab, search for the element that owns the motion, per-frame sampler | nothing visible; every layer below uses it | `chrome.scripting.executeScript({world: 'MAIN', func})` under activeTab | the page can read and fake MAIN-world messages |
| 1 | Record → fit → WAAPI preview, plus the agent payload | edit, preview, slow, scrub, compare and hand back motion from any library that writes inline styles, WAAPI or CSS | content script (isolated world, inferred) | a stand-in for the real code; page inline `!important` and animations created later beat it |
| 2 | Virtual clock, late install, `release()` | page-wide 0.1–1× speed, pause and frame step of the page's real motion | MAIN, no reload | timers created before install keep real time; time only runs forward |
| 3 | Motion adapter: fiber read-back, `getDefaultTransition`, `animationState` replay, `__MOTION_INSPECT__` | edits run through Motion itself; per-animation seek in both directions; the exact authored transition | MAIN | fiber path is React-only; hook needs motion-dom ≥ 13.3; both rely on undocumented internals |
| 4 | Reload mode: CDP document-start install of clock and hook | the clock also catches autoplay timers; the hook also catches load animations | debugger attached for the reload only | the reload drops page state; infobar shows during the reload |
| 5 | GSAP, Swiper and anime.js adapters | `timeScale`, `duration`/`ease`, `params.speed`, `engine.speed` | MAIN | GSAP `timeScale` on a single tween is unreliable when a parent timeline drives it |
| 6 | CDP expert fallbacks: heap discovery and conditional breakpoints | Motion on non-React pages, and any minified library | debugger; stays attached for the whole preview when breakpoints are used | 0.14–0.25 ms per breakpoint hit; heap patches survive detach |

Layers 2 and 3 do not depend on each other, so you can build them in parallel. Everything through layer 3 runs on the `activeTab` and `scripting` permissions already in `extension/manifest.json`.

### The floor imitates the motion instead of patching the code

Start where Snapshot already is. `sample()` records boxes and matrices, sampled recordings already replay as keyframes with `fill: 'forwards'` (`extension/src/content.ts:106–135`), and the panel already wires speed and scrub to `onSpeed` and `onSeek` (`content.ts:457–458`). Three changes turn that into a motion editor. The first is finding the motion owner: walk up from the selection to the nearest ancestor whose own transform moves by the same amount as the selection's box during the move, which on flora is the track. The second is recording every frame while a value changes and keeping only sparse rows while it holds. Today's `interval = max(16, duration/720)` (`extension/src/extract.ts:238`) drops to 12 Hz on a 60 s recording, leaving about a dozen points per move, and in one test run a six-parameter cubic-bezier overfit them and beat the spring.

The third change is fitting each move twice, once as a damped oscillator with a free start time and a Huber loss so one late frame cannot drag it, and once as a cubic-bezier, then choosing by BIC. Across 16 flora fits the spring won every time by **ΔBIC 28–147**, except one 30 Hz move that tied at 2.3 and went to the spring because its samples overshoot; spring RMSE was **0.16–0.31 px** on clean moves (`scripts/fit-flora-sample.mjs`, `scripts/fit-core.mjs`). On motion of known origin the fitter recovered `cubic-bezier(0.201, 0.797, 0.203, 0.998)` from a CSS transition and identified a JS `power3.out` as exactly `cubic-bezier(1/3, 1, 2/3, 1)` (`scripts/fit-local-models.mjs`). In Node the spring fit takes about 100 ms per move and the bezier about 1.07 s, so run the fit off the content script's thread, spring first.

The preview is `element.animate()` on the property the owning element actually writes, using the `linear()` string Motion itself would generate (10 ms points, ported in `scripts/fit-motion-spring.mjs`), with `fill: 'forwards'` and `composite: 'replace'`. In Chromium this animation beats the normal inline style Motion writes every frame, a running CSS transition, and any page WAAPI animation created before it, but loses to inline `!important` and to page animations created after it (`scripts/fit-local-cascade.mjs`; [CSS Cascade 5](https://www.w3.org/TR/css-cascade-5/#cascade-origin)). Three preview modes worked on flora (`scripts/fit-flora-preview.mjs`). Replay in place plays from the position before the last move to the current one, so it ends where the page already is. Intercept starts the edited move inside a MutationObserver callback at the page's own move start, and it replaced Motion's motion from the same frame. Mid-move hand-back uses a `composite: 'add'` offset that decays to zero when the page starts moving under the preview ([MDN composite](https://developer.mozilla.org/en-US/docs/Web/API/KeyframeEffect/composite)); it turned a **255.7 px one-frame jump into 0 px**, with a largest step of 24.8 px per frame against the page's own peak of about 30.

Slow motion and scrubbing come with WAAPI for free. At `playbackRate 0.25`, 179 ms of animation advanced per 700 ms of wall time, and paused seeks landed within 0.10 px of the analytical curve. A ghost clone playing the original fit beside the edit cleaned up exactly, but default to a ghost outline drawn in Snapshot's own overlay instead, because a clone inserted into a React-owned parent could be disturbed when React re-renders that parent, and nobody tested that. The floor's limit is that it is a stand-in. It shows the edited curve on the real element without running the page's code, so retargeting, gesture velocity and autoplay timing stay the page's original behaviour underneath. It fits one value at a time and has not been tried on multi-keyframe sequences, inertia, interrupted springs or 2D paths. Distrust its model choice below about 20 samples, and re-create the preview at the same `currentTime` whenever the page creates a newer animation on the same property, which Motion 14.2+ does when it rebuilds a `TransformAnimation`.

### One clock drives every timeline, and it is released rather than unplugged

The clock computes `virtual = anchorV + (real − anchorR) × rate`, re-anchors on every rate change, and never lets time run backwards. It patches `performance.now`, `Date.now`, `new Date()` and `Event#timeStamp`, wraps `requestAnimationFrame` and `cancelAnimationFrame`, keeps timers on its own virtual queue, and manages the `playbackRate` and `startTime` of `document.getAnimations()` (`scripts/clock-vclock.mjs`). Ship it as one self-contained packaged function injected with `chrome.scripting.executeScript({world: 'MAIN', func, args})`; `func` is serialized, so it cannot close over anything, and `args` must be JSON ([chrome.scripting](https://developer.chrome.com/docs/extensions/reference/api/scripting)). It installs at rate 1, so the page sees no change until you move the dial.

A late install gets flora's spring exactly right: at 0.25× the move took 2216 ms over 133 frames with the 2.22 px overshoot intact (`scripts/clock-late.mjs`). Pause keeps rAF firing with a frozen timestamp, so the page stays responsive, and an `ArrowRight` pressed while paused still advanced React state. Stepping by 16.67 ms is frame-exact: the spring settled after **33 steps, which is 550 ms**, matching `duration: 0.55` (`scripts/clock-docstart.mjs`). Rate changes mid-spring do not jump; the largest step during a 0.5× → 1× change was 16.8–16.9 px, below the 1× move's own largest step of about 32 px (`scripts/clock-release.mjs`).

Two hazards are real, and the clock handles both. Motion sets each WAAPI animation's `startTime` from the virtualized `performance.now()` while `document.timeline` keeps real time, and without translating those writes a Motion-style WAAPI animation started **4578–4591 ms in instead of 4 ms**, jumping straight to its end (`scripts/clock-waapi.mjs`). Removing the clock while something moves lands all the accumulated lag inside the spring at once: `uninstall()` mid-move at 0.1× snapped 62 px in one frame. `release()` instead goes to 1× immediately, lets the move finish (783 ms, no snap), and uninstalls only after the selected subtree has been quiet for 250 ms, so the jump lands while nothing moves, at 0.00 px (`scripts/clock-late.mjs`, `scripts/clock-release.mjs`). After release every patched global is native again, pending timers move to native timers with their remaining delay, and `clearInterval` on an id created under the clock still worked.

The clock has hard walls. **A late clock cannot capture timers that already exist.** Flora's autoplay `setInterval` kept firing every 5 s of real time during pause, and a stepped move then changed target mid-way and travelled two pages (`scripts/clock-late.mjs`), so say so in one line ("Timers that started before slow motion keep real time. Reload to include them.") and offer the reload mode. **It only runs forward**, because Motion clamps `startTime = Math.min(startTime, timestamp)` and a backwards clock corrupts animations ([JSAnimation.mjs](https://unpkg.com/motion-dom@14.1.0/dist/es/animation/JSAnimation.mjs)); scrubbing the real page backwards needs the Motion hook's `.time` or the floor's stand-in. **It misses libraries that kept their own copy of a clock function at load.** GSAP stores `Date.now` as `_getTime` when its module loads ([gsap.js](https://unpkg.com/gsap/dist/gsap.js)), so drive `gsap.globalTimeline.timeScale()` there instead; this is source-read, and nobody ran GSAP under the clock. It also leaves `Temporal.Now` (present in Chromium 158), `requestIdleCallback` deadlines, audio and media clocks, `requestVideoFrameCallback`, workers and cross-origin frames on real time, and every same-origin frame needs its own clock via `allFrames: true`. One integration detail is inferred rather than measured: the clock resets the `playbackRate` of everything in `document.getAnimations()` each frame, Snapshot's own previews included, so mark those and let one speed dial drive both on purpose.

### The Motion adapter turns the stand-in into the real thing

On React sites, reach Motion's VisualElement through the fiber. Read the node's `__reactFiber$<suffix>` property (one random suffix per copy of React), walk `.return` up to the `MotionContext.Provider` whose `memoizedProps.value.visualElement.current === node`, and if that misses, scan the hooks of the fiber whose `elementType` carries `Symbol.for('motionComponentSymbol')` (`scripts/library-flora-motion-fiber.mjs`). The same structure exists from framer-motion 11.18.2 through 14.14.0 ([framer-motion 14.14.0 motion/index.mjs](https://unpkg.com/framer-motion@14.14.0/dist/es/motion/index.mjs), [11.18.2](https://unpkg.com/framer-motion@11.18.2/dist/es/motion/index.mjs)), and every property name the walk needs survived flora's minification. Ship this read-only lookup early, alongside the floor. It returns the authored transition exactly, `{type: "spring", duration: 0.55, bounce: 0.16}`, and comparing it with the fit is a cheap check: when they disagree, a variant, an override or a WAAPI handoff is driving the motion instead.

To edit, override `getDefaultTransition` on the instance. `animateTarget()` calls it on every start, and React re-renders replace `props` without touching the instance method, so the override sticks while `ve.props.transition` keeps reading the original ([visual-element-target.mjs](https://unpkg.com/motion-dom@14.14.0/dist/es/animation/interfaces/visual-element-target.mjs)); `delete ve.getDefaultTransition` reverts exactly. To preview on demand through Motion's own pipeline without touching React state, jump the MotionValue back to its previous target, delete that key from `animationState.getState()[type].prevResolvedValues`, and call `animateChanges()`. That replay started in **1–2 ms**, against 3–6 ms for dispatching the carousel's own `ArrowRight` and 5 ms for calling the index hook's `queue.dispatch`. Prefer the replay, because picking a `useState` hook by matching its value is a guess, and dispatching to the wrong one corrupts app state that only another dispatch can undo. Production React offers nothing safer: `overrideProps`, `overrideHookState` and `scheduleUpdate` exist only in development builds ([react-dom production client](https://unpkg.com/react-dom@19.3.1/cjs/react-dom-client.production.js)). For slider edits during a move, restart `duration`/`bounce` springs from rest rather than retargeting them. Since 13.x Motion deliberately drops inherited velocity for these springs ([13.5.1 spring.mjs](https://unpkg.com/motion-dom@13.5.1/dist/es/animation/generators/spring.mjs)), and the measured retarget nearly stopped the track, with per-frame steps falling from −28.5 px to −0.7 px, while a stiffness-and-damping spring carried its velocity through smoothly.

Add the inspector hook for what fibers cannot reach. Installed late and filtered to `record.options.element === ve`, it receives the live animation and its options object, and rewriting `duration` and `bounce` before calling `record.animation.initAnimation()` changes the spring. This path also catches inline `animate.transition`, variant transitions, `transitionOverride`, imperative `animate()` calls and Motion on non-React pages, all of which the `getDefaultTransition` override misses. The live handle gives per-animation control the clock cannot: `pause()` held `time` steady, `time = 0.3` put the track at −1152.19 against a −1152 target, and `time = 0.05; speed = 0.25; play()` finished in 2000 ms, exactly (0.55 − 0.05) / 0.25 (`scripts/library-flora-motion-inspector.mjs`). Chain to any hook already installed and restore it afterwards through property descriptors, because Motion Studio's tooling may own it.

The hook's limits are sharp. It exists only from **motion-dom 13.3.0 (2026-09-14)** and is absent in 12.x and in 13.0–13.2 ([Motion CHANGELOG](https://github.com/motiondivision/motion/blob/main/CHANGELOG.md)). It is not public API: Motion's own code comment calls it a "raw firehose" that avoids "adding a public Motion API", and the changelog warns that undocumented APIs "may change without warning". `initAnimation` is an internal method name that happens to survive minification today. Spring rewrites only apply to JS-driven animations, because a WAAPI-backed `NativeAnimation` has already passed its keyframes to `element.animate` (source-read, not executed). On 14.2+ sites where `x` runs on WAAPI, edit through `getDefaultTransition`, which Motion reads before it chooses JS or WAAPI (inferred, untested), and fall back to the floor where that fails. Under the OS reduced-motion setting, Motion forces `{type: false}` on position keys and flora switches to `{duration: 0}`, so the adapter's previews are instant; the floor's stand-in still plays when the person asks for it.

### CDP is worth its infobar only for reloads and last resorts

CDP gives Snapshot exactly one thing it cannot otherwise get without new permissions: running a script before the page's own scripts. The sequence `Page.enable` → `Page.addScriptToEvaluateOnNewDocument({source})` → `Page.reload` → wait for `Page.loadEventFired` → `Page.removeScriptToEvaluateOnNewDocument` → detach in a `finally` block installed the clock ahead of page scripts; it survived detach, and the registration died with the session, so the next reload was clean (`scripts/clock-cdp-inject.mjs`). Skipping `Page.enable` made the script silently never run (`scripts/debugger-reload-rewrite-flora.mjs`). With the clock installed at document start, flora's 5 s autoplay stretched to **17,533 ms real at 0.25×** against a predicted 17.6 s, and an 8 s pause produced no autoplay at all (`scripts/clock-docstart.mjs`).

Build `source` from the packaged function's `toString()` plus JSON options, never from fetched code, because the MV3 policy exempts code run through the Debugger API only for "the specific section of code covered" ([MV3 requirements](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements)). The alternative, `registerContentScripts` in the MAIN world at `document_start`, needs host permissions according to Extension.js, while MDN says activeTab is enough ([MDN](https://developer.mozilla.org/docs/Mozilla/Add-ons/WebExtensions/API/scripting/registerContentScripts), [Extension.js](https://extension.js.org/docs/implementation-guide/inject-scripts)); the CDP route avoids the question. Name the button after its outcome and warn before reloading, because the reload drops page state such as scroll position and open menus, and drops Snapshot's own selection too unless you save it in `chrome.storage.session` and re-inject `content.js`.

Keep the remaining CDP techniques as expert fallbacks. `Runtime.queryObjects(Function.prototype)` listed 7,047 functions in 108 ms, and fingerprinting their source on property names that survive minification (`scrapeMotionValuesFromProps`, `canTrackVelocity`, `getDefaultTransition`, `isResolvedFromDuration`) found Motion's VisualElement class and its 9 live instances, which is how to reach Motion on a non-React page (`scripts/debugger-live-patch-flora.mjs`). A breakpoint whose condition reads like `(mutate(e), false)` rewrites values without ever pausing, works on any library's minified code and reverts automatically on detach, but each hit cost **138,888–250,570 ns against 0.8 ns** without the debugger (`scripts/debugger-breakpoint-cost-and-clients.mjs`). Put such breakpoints only on functions that run once per animation, such as the spring generator, and pin them by `scriptHash`, because Next.js chunk URLs change on every deploy. Patches made to page objects through CDP persist after detach, so record them in the undo ledger and revert them on `chrome.debugger.onDetach`, which fires when the user opens DevTools ([chrome.debugger](https://developer.chrome.com/docs/extensions/reference/api/debugger)).

One collision is certain. The same extension cannot attach twice to one tab ("Another debugger is already attached…", `scripts/debugger-extension-probe-flora.mjs`), and Snapshot's screenshot code in `extension/src/background.ts` attaches and detaches around each capture, so all debugger use has to go through one shared session manager. Avoid rewriting script bodies with `Fetch`. Without a cache-bypassing reload it never even intercepted flora's immutable Motion chunk, and a patched body served with the original cache headers stayed in the tab after `Fetch.disable`, still measuring 1665 ms on a plain reload, unless it was served `no-store` (`scripts/debugger-fetch-cache-poisoning-flora.mjs`). Subresource integrity hashes and service workers break the technique on other sites, and declarativeNetRequest cannot edit response bodies at all ([DNR](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest)).

### GSAP and Swiper expose handles, while most carousels do not

GSAP installs `window.gsap` even when bundled as ES modules ([gsap-core.js](https://unpkg.com/gsap@3.15.1/gsap-core.js)). On gsap.com, `globalTimeline.timeScale(0.5)` stretched a 0.5 s tween from 486–492 ms to 1000–1016 ms and restoring it returned 500–516 ms, while editing a site tween's `duration()` and `vars.ease` followed by `invalidate()` reverted exactly (`scripts/library-gsap-swiper.mjs`). Swiper attaches its instance as `el.swiper`, and setting `params.speed` changed the next slide from 300 ms to 1500 ms and back. anime.js v4 registers `window.AnimeJS[i].engine` with a `speed` setter ([anime.js globals](https://unpkg.com/animejs@4.5.0/dist/modules/core/globals.js)), which is source-read only. Embla, Keen, Splide, react-spring and Rive attach nothing reachable in production builds, so on those pages Snapshot relies on the floor and the clock.

## Send the agent the source's own spring form, not the dial's

### Duration, visualDuration and physics describe three different springs

The hand-off is where a production tool proves its worth, and it has one trap. DialKit 2.0.2's `SpringConfig` offers `visualDuration`, `bounce` and physics fields but **no `duration`** ([DialKit index.d.ts](https://unpkg.com/dialkit@2.0.2/dist/index.d.ts)), and the three spring forms are not interchangeable. Flora's `duration 0.55, bounce 0.16` resolves to stiffness 252.7 and damping 26.7, which equals `visualDuration 0.329`; writing `visualDuration 0.55, bounce 0.16` instead would give stiffness 90.6 and damping 16.0, a much slower spring (`scripts/fit-motion-spring.mjs`). The forms also end differently. A `duration` spring starts from rest and ends exactly at `duration` with a sub-pixel snap to the target, while every other form inherits velocity and ends when it falls below rest thresholds ([spring.mjs](https://unpkg.com/motion-dom@14.14.0/dist/es/animation/generators/spring.mjs)).

So seed the spring dial from the fit, show the source's form beside it, and convert the edited physics back to that form when you send. The source form comes from the read-back. Without one, the snap is the tell: flora's moves snapped 0.322 px onto the target 559.6–560.1 ms after the fitted start (`scripts/fit-flora-sample.mjs`). Show settle time next to "duration" as well, because the spring first reaches its target at roughly 300–330 ms for both 0.55 s and 1.5 s springs (`scripts/library-flora-motion-fiber.mjs`).

### Grep keys stand in for flora's missing source maps

For each edited element, send the selector of the element that owns the motion and its component, the detected library with its evidence, the read-back transition marked as untrusted page data, the fit with its RMSE, max error and ΔBIC, the edited model in the source's form plus its CSS `linear()` equivalent, whether it was previewed, and grep keys. Flora needs the grep keys: its chunks carry no `sourceMappingURL` and the `.map` URL returns 403 (`scripts/debugger-reload-rewrite-flora.mjs`), while the strings `"Journal carousel"`, `springDuration` and `springBounce` survive minification and point an agent straight at the component.

All of this fits today's schema without breaking it. `CaptureAnimation.timing` is already `Record<string, unknown>` (`core/capture.ts:33–44`), so `timing.fit`, `timing.edit` and `timing.library` work now, and one `motionChanges` entry puts the change into the note's existing "Apply these changes…" line (`extension/src/content.ts:639–642`). A prompt line in that spirit reads: "Carousel track (`motion.div`, `animate={{ x }}`) uses `transition={{ type: "spring", duration: 0.55, bounce: 0.16 }}` (read from props; fit 0.55 / 0.16, RMSE 0.25 px). Change it to `{ type: "spring", duration: 1, bounce: 0.4 }`. Previewed: 27 px overshoot on a 288 px move." For other libraries, write the same model in their own syntax: a GSAP `CustomEase` built from the bezier points or from an SVG path traced through the spring, since GSAP's core has no spring, or a CSS `transition: transform 1000ms linear(…)` with a fallback transition declared first ([Motion CSS docs](https://motion.dev/docs/css)).

### Motion Studio rejects stale edits, and stops short of production

Borrow one more idea from Motion Studio, the closest existing product, whose Apply step "rejects stale edits if the source changed after the preview was made" ([Motion Studio docs](https://motion.dev/docs/studio)). Record the chunk's `scriptHash` and the read-back when the preview is made and include them in the payload, so the agent, or Snapshot at send time, can tell whether the site has been redeployed since. Motion Studio also marks where Snapshot has room. It needs a bundler plugin, a companion server and Motion 13.3 or later, and "Production builds exclude Studio". None of the agent-annotation tools surveyed, Agentation, react-grab and Cursor Design Mode among them, sends spring parameters or recorded motion to agents ([Cursor Design Mode](https://cursor.com/blog/design-mode)), so production motion context is open ground.

## Every layer needs its own revert, guardrail and honest limit

### Eight techniques need eight different reverts

There is no single revert mechanism. Give every layer an entry in a per-tab undo ledger, and run the ledger on Discard, Escape, navigation, tab hide, Snapshot close and debugger detach.

| Layer | Revert | What lingers if Snapshot dies mid-preview |
|---|---|---|
| WAAPI stand-in | `cancel()` when it ends at the page's target, or a `composite: 'add'` hand-back mid-move; remove the ghost | nothing beyond the running animation |
| Virtual clock | `release()`: back to 1×, then uninstall after 250 ms of quiet (8 s cap) | patched globals until reload; after a document-start install, wrappers that behave natively but are not the original functions |
| `getDefaultTransition` override | `delete` the property on the instance | the override, until reload |
| `__MOTION_INSPECT__` | restore the previous property descriptor | the hook, until reload |
| Conditional breakpoint | `removeBreakpoint`, or detach | nothing (it dies with the debugger connection) |
| Patch to page objects via CDP, including `[[Scopes]]` | restore the original from the ledger | the patch, until reload |
| Document-start script | `removeScriptToEvaluateOnNewDocument` | nothing (it dies with the session) |
| Fetch rewrite (avoid) | `Fetch.disable` plus a cache-bypassing reload | the patched chunk in that tab's cache |

### Everything the MAIN world says is untrusted data

The MAIN world is shared with the page, so treat it as hostile ground. A page that hooked `addEventListener` before Snapshot ran learned Snapshot's "secret" event name, and `isTrusted` is false for faked and genuine events alike (`scripts/clock-channel.mjs`, which used a CDP isolated world in place of Snapshot's content script). A random per-install event name therefore only prevents accidental collisions. Validate every MAIN → isolated message and use it as display data only, and never let one trigger capture, upload or native messaging, a permission Snapshot holds. A faked rate command can only change the page's own clock, which the page could do anyway. The same rule reaches the agent: read-back props and fiber strings are page-controlled text that ends up in a coding agent's prompt, so quote them as data. Keep the installers free of `eval` as well, since code in the main world runs under the page's Content Security Policy ([content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)); flora has no CSP, and pages with a strict one are untested.

### Drive GSAP on the page, but never bundle it

Licences limit which code you may copy, not which libraries on the page you may drive. Do not bundle GSAP or GSDevTools: GSAP's free licence prohibits tools that let people build visual animations without code in competition with Webflow's own animation tools, and a timing editor plausibly counts, while driving a page's own GSAP instance redistributes nothing (an inference, not legal advice) ([GSAP Standard License](https://gsap.com/community/standard-license/)). Theatre.js Studio is AGPL-3.0 and Agentation is PolyForm Shield, so reuse code from neither ([Theatre](https://github.com/theatre-js/theatre), [Agentation](https://github.com/benjitaylor/agentation)). react-grab and bippy (MIT), timeweb (BSD-3-Clause) and DialKit (MIT, already a dependency) are fine to reuse.

### Label each animation with what Snapshot can do to it

Show the limits where they apply instead of hiding them. Give each detected animation one state, "Editable", "Slow-mo only", "Read-only: set by code" or "Needs reload to control", each with its reason and one next step. That follows Motion Studio, which shows values set by code expressions as read-only, and the repo's own "error in place: what + recovery" rule. For the keyboard, copy GSDevTools, where Space plays and pauses and the arrow keys change the time scale ([GSDevTools](https://gsap.com/docs/v3/Plugins/GSDevTools/)).

So the first engineering step is a validation pass, not a feature, and it takes five checks. Load the existing installers, `installVirtualClock` from `scripts/clock-vclock.mjs` and the self-contained `installVellumMotion` from `scripts/library-flora-motion-fiber.mjs`, through `chrome.scripting.executeScript({world: 'MAIN'})` from the real Snapshot service worker. Rerun the flora measurements in headful Chrome and in Dia. Start a preview `element.animate()` from the isolated content script. Send messages over the channel between the real isolated and MAIN worlds. Finally, run the CDP reload mode once, to see whether activeTab survives it and what Dia does with the infobar. If those checks reproduce the headless numbers, the build order above stands. If MAIN-world injection misbehaves in Dia, the floor still works, and that is exactly why the floor comes first.

## Conclusion

The `debugger` permission matters less to this feature than you would expect. Everything through the Motion adapter runs on `activeTab` and `scripting` with no infobar, and CDP's real contribution narrows to running a script before the page's own, through a permission you already hold, which beats asking for host permissions for `registerContentScripts`. Its famous live-edit power is gone and its virtual-time switch breaks the tab. That reverses the obvious plan: the safest and broadest techniques, a WAAPI stand-in and a clock that is released rather than unplugged, carry the product, and the deepest ones become fallbacks.

The no-reload control on flora also rests on two Motion implementation choices, reading `performance.now()` fresh every frame and reading the inspector global on every call. A point release could undo either, for instance by switching to manual timing or caching its own copy of the clock function, so build the adapters to detect what they find and degrade to an honest state label rather than assume. The lasting asset is not any one hook but the motion record: the read-back, the fit and the previewed edit, in the source's own form. No production tool sends that to agents today, and when the fit disagrees with the read-back, the disagreement is itself a finding worth showing the user.
